## 1. Что это

Оркестратор на базе **CrewAI 1.15**, который по текстовому описанию задачи генерирует production-ready веб-сервис, создаёт Pull Request в GitHub и пытается добиться зелёного CI через автоматический fix loop.

**Эталонная задача:** URL shortener (FastAPI + SQLite, без ORM) — создать короткую ссылку, редирект, статистика переходов.

## 3. Ключевые технические решения

### 3.1 Модели (OpenRouter)

| Роль | Модель | $/1M in/out | Обоснование |
|---|---|---|---|
| Архитектор | z-ai/glm-5.2 | 1.40/4.40 | Сильный reasoning для дизайна |
| Test Designer | deepseek/deepseek-v4-pro | 0.44/0.87 | Лучше пишет код (тесты = код) |
| Разработчик | deepseek/deepseek-v4-pro | 0.44/0.87 | ≈ Sonnet 4, в 6 раз дешевле |
| QA Gate | mistralai/codestral-2508 | 0.30/0.90 | Специализирован на коде |
| DevOps | deepseek/deepseek-v4-pro | 0.69/1.37 | Инфраструктура = код |

**⚠️ Известный баг:** у deepseek-v4-pro две разные цены в config.py (`:23` — 0.44/0.87, `:37` — 0.69/1.37).

### 3.2 Структурированный вывод

- Все file-producing задачи используют CrewAI `output_pydantic=CodeOutput` (JSON `{"files": [{path, content}]}`)
- Fallback: regex-парсинг markdown code blocks (`_extract_files`)
- Path traversal guard + запрет абсолютных путей (`_write_file_safe`)
- Коллизии имён: `.collision` суффикс + обработка «файл vs директория с одним именем»
- Экстракция файлов ТОЛЬКО из ролей {test designer, разработ, devops} — Архитектор и QA не производят файлов

### 3.3 Паттерн-библиотека (`patterns/`)

4 markdown-файла с best practices, внедряемые в промпты:
- `architecture-agents.md` — DI, структура по доменам
- `fastapi-agents.md` — FastAPI 0.115+, Pydantic 2.7, compat matrix (адаптировано из zhanymkanov/fastapi-best-practices)
- `docker-agents.md` — multi-stage, non-root, pinned versions
- `pytest-agents.md` — pytest-asyncio, fixtures, ASGITransport

### 3.4 PR-автоматизация

- `git worktree` (не stash) — не трогает рабочее дерево оркестратора
- Дедупликация: закрывает stale PR той же задачи
- GitHub REST API через PAT (GITHUB_TOKEN в .env)

### 3.5 CI fix loop

- `_wait_for_ci_run` — поллинг GitHub Actions API (timeout 600s)
- `_get_ci_failure_logs` — извлечение логов failing job (до 6000 chars)
- `_run_ci_fix` — отдельный Crew из одного Разработчика: arch_doc[:2000] + CI logs → полная кодовая база
- `_push_fix_to_pr` — коммит и push в ту же ветку
- `MAX_CI_FIX_ATTEMPTS = 3`

## 5. Системные проблемы (для ревьюера)

### 🔴 Критичные

**P1. «Промпт-патчинг» вместо верификации на земле.**
Оркестратор чинится исключительно добавлением КРИТИЧНО-блоков в промпты (11 фиксов за день). Это работает как whack-a-mole: модель может игнорировать любой из 20+ «КРИТИЧНО» в одном промпте. Нет ни одного программного чека между генерацией и PR: ни `py_compile`, ни локального pytest, ни проверки «main.py подключает routers». **Парадокс:** у QA Gate есть инструмент `run_tests` (реальный pytest в venv), но его вердикт не блокирует создание PR.

**P2. Дублирование ответственности = гарантированный дрейф.**
Система сознательно генерирует артефакты независимо: Test Designer (тесты) → Разработчик (код) → DevOps (CI). Они видят друг друга только через контекст CrewAI (обрезанный). Пример из #16: Разработчик написал монолит `app/main.py` (aiosqlite, 302) И `app/routers/` (sqlite3, 307) — две разные реализации одного API в одном прогоне, main.py роутеры не подключает. Test Designer написал тесты на `custom_code`, которого нет в архитектуре.

**P3. QA Gate не является gate.**
- `run_tests` создаёт venv и ставит зависимости заново при каждом вызове — 1-2 мин на прогон
- Вердикт No-Go не блокирует: PR создаётся при любом `status == "✅ Успешно"` (это статус Crew, не QA)
- `MAX_REVIEW_CYCLES = 1` мёртв: fix_task запускается безусловно в pipeline (только если QA вернёт No-Go — логика в промпте, не в коде)

### 🟡 Важные

**P4. Метрики частично фиктивны.** `_estimate_cost` использует средневзвешенную цену всех моделей (CrewAI не даёт per-agent токены). Реальные токены читаются из `result.token_usage` — но если провайдер не вернул usage, в отчёте 0.

**P5. Fix loop работает вслепую.** Разработчик в fix loop получает arch_doc[:2000] + 6000 chars логов, но НЕ видит текущий код и НЕ видит тесты. Он регенерирует всю кодовую базу целиком — риск регрессий и потери ранее работавших частей. Нет diff-подхода (по мотивам Nx Self-Healing CI — в бэклоге).

**P6. Размножение PR.** 17 PR за день (#3…#17), все по одной задаче. Дедупликация (`_close_stale_prs`) закрывает старые, но история ветвления замусорена.

**P7. Зависимость промптов от конкретной задачи.** В промптах жёстко прописано: «endpoints: /shorten, /health, /{short_code}, /stats/{short_code}» — оркестратор перестал быть задаче-агностичным. Для другой задачи эти требования вредны.

### 🟢 Архитектурные вопросы к ревьюеру

1. **TDD правильно реализован?** Test Designer и Разработчик используют ОДНУ модель (deepseek-v4-pro) — не является ли это скрытой подгонкой (модель «помнит» стиль своих тестов)? Стоит ли разнести на разные модели для истинной независимости (AgentCoder)?

2. **Куда двигаться:** дальше ужесточать промпты ИЛИ вводить программные ворота (локальный pytest до PR, py_compile, schema-валидация структуры проекта)? Какой минимальный набор чеков закрыл бы 80% наблюдаемых фейлов?

3. **Fix loop: diff vs full-regen?** Nx Self-Healing CI показывает, что diff + human approve эффективнее полной регенерации. Но diff требует от модели точного знания текущего состояния файлов — как это дать ей дешевле, чем пересылать всю базу?

4. **Стоит ли QA реальным gate:** запускать pytest оркестратором (не агентом) ПЕРЕД созданием PR, и не создавать PR при красных тестах? Цена: лишние 1-2 мин и $0 (локальный запуск) на прогон.

5. **Одна модель на всё?** DeepSeek V4 Pro ($0.44/$0.87) справляется не хуже специализированных моделей. Упростить до 2 моделей (reasoning + code)?
