# QA Gate

## Задача

        Проверь код Разработчика на соответствие архитектурному документу Архитектора.

        ЧТО ПРОВЕРЯТЬ:
        1. **Соответствие архитектуре**: все ли компоненты реализованы? Нет ли лишнего?
        2. **Безопасность**: SQL-инъекции, XSS, утечки секретов, небезопасные зависимости
        3. **Обработка ошибок**: все ли исключения обработаны? Нет ли голых try/except?
        4. **Валидация**: проверяются ли входные данные на всех endpoint-ах?
        5. **Тесты**: есть ли они? Покрывают ли основные сценарии?
        6. **Style guide**: PEP 8, нейминг, типизация

        ФОРМАТ ОТВЕТА:
        Для каждой найденной проблемы:
        - Приоритет: 🔴 (критично — блокирует запуск) / 🟡 (важно — нужно исправить) / 🟢 (минор — можно так)
        - Файл и строка (если применимо)
        - Описание проблемы
        - Предложение по исправлению

        В конце: ИТОГОВЫЙ ВЕРДИКТ — ✅ Go (нет критических проблем) или ❌ No-Go (требуются правки).
        Если No-Go — перечисли КОНКРЕТНЫЕ файлы и строки, которые нужно исправить.
        

## Результат

## Отчёт о проверке кода

### 🔴 Критические проблемы (блокируют запуск)

1. **Файл:** `app/routers/redirect.py`, строка 32  
   **Проблема:** Background task `increment_clicks` получает `db_session`, который является зависимостью FastAPI и будет закрыт после завершения запроса. Попытка выполнить запрос к БД в фоновой задаче приведёт к ошибке `DetachedInstanceError` или `Session is closed`.  
   **Предложение:** Создавать новую сессию внутри background task (через `async_session_factory`) или использовать отдельный механизм (очередь). Пример:
   ```python
   async def increment_clicks_background(short_id: str):
       async with async_session_factory() as session:
           await increment_clicks(session, short_id)
   background_tasks.add_task(increment_clicks_background, short_id)
   ```

2. **Файл:** `app/middleware/rate_limiter.py`, строки 30–40  
   **Проблема:** При недоступности Redis вызов `redis_client.pipeline()` выбросит исключение, которое не обрабатывается. Согласно архитектуре, при недоступности Redis сервис должен работать в режиме "fail-open" (пропускать запросы).  
   **Предложение:** Обернуть блок работы с Redis в `try/except` и при любой ошибке возвращать `True` (разрешить запрос), логируя предупреждение. Пример:
   ```python
   try:
       async with redis_client.pipeline(transaction=True) as pipe:
           ...
   except Exception:
       logger.warning("Redis unavailable, rate limiting disabled")
       return True
   ```

### 🟡 Важные проблемы (рекомендуется исправить)

3. **Файл:** `app/services/url_service.py`, строки 38–48  
   **Проблема:** При наличии кэша (cache hit) функция всё равно выполняет запрос к БД (`db_session.get(URLRecord, short_id)`), что снижает производительность read-path. Архитектура предполагает, что кэш хранит `original_url`, и при cache hit можно сразу вернуть URL без обращения к БД.  
   **Предложение:** Оптимизировать: при cache hit возвращать минимальный объект (например, `URLRecord` с заполненным `original_url` и `deleted=False`) или кэшировать полную запись в JSON. Для MVP можно оставить, но желательно исправить.

4. **Файл:** `app/utils/id_generator.py`, строка 33  
   **Проблема:** Используется `random.randrange` для генерации ID. Для production-среды рекомендуется криптостойкий генератор (`secrets.randbelow`), чтобы избежать предсказуемости коротких ссылок.  
   **Предложение:** Заменить `random.randrange` на `secrets.randbelow(MAX_ID_VALUE)`.

5. **Файл:** `tests/conftest.py`, строка 120 (патч `redis_client`)  
   **Проблема:** Патч модулей через `__import__` и прямое присвоение атрибутов может не сработать, если модули уже импортированы в других местах. Лучше использовать `unittest.mock.patch`.  
   **Предложение:** Использовать `mock.patch.object` для замены `redis_client` в каждом модуле.

### 🟢 Минорные проблемы (можно оставить)

6. **Файл:** `app/routers/redirect.py`, строка 18  
   **Проблема:** Отсутствует валидация `short_id` (длина, символы). Хотя архитектура не требует строгой проверки, это может привести к неожиданным ошибкам при передаче некорректных ID.  
   **Предложение:** Добавить Pydantic-модель для path-параметра или проверку в сервисе (например, `len(short_id) == 7 and all(c in BASE62_ALPHABET for c in short_id)`).

7. **Файл:** `app/main.py`, строка 56  
   **Проблема:** В `lifespan` используется `select(1)` без импорта `select` (импорт добавлен в коде, но в предоставленном файле он есть — строка 8). Всё корректно.  
   **Комментарий:** Ошибки нет.

8. **Файл:** `tests/test_redirect.py`, строка 33  
   **Проблема:** Тест не проверяет инкремент кликов из-за проблемы с background task (см. критическую проблему 1). После исправления background task тест можно дополнить.  
   **Предложение:** После исправления background task добавить проверку clicks через `GET /stats/{id}`.

9. **Файл:** `app/schemas/url.py`, строка 16  
   **Проблема:** `field_validator` не выполняет никакой дополнительной проверки. Можно удалить или добавить SSRF-защиту (как закомментировано).  
   **Предложение:** Удалить пустой валидатор или реализовать проверку приватных IP.

10. **Файл:** `app/middleware/rate_limiter.py`, строка 22  
    **Проблема:** Класс `RateLimitExceeded` объявлен, но нигде не используется.  
    **Предложение:** Удалить неиспользуемый класс.
